# BenHouse v0.4 — UX, Navegación y Experiencia de Usuario

## Objetivo

Definir la experiencia de usuario oficial de BenHouse v0.4.

Este documento debe impedir:

- navegación basada en módulos técnicos;
- exceso de dashboards;
- interfaces fragmentadas;
- duplicación de pantallas;
- sobrecarga de métricas;
- uso excesivo de IA como reclamo;
- pérdida de continuidad entre búsqueda, decisión y operación.

BenHouse debe sentirse como una experiencia inmobiliaria continua, no como una colección de herramientas independientes.

---

# 1. Principio maestro

La interfaz debe responder a lo que el usuario quiere hacer, no a cómo está organizado el backend.

El usuario no debe pensar en:

- contratos;
- pagos;
- documentos;
- ofertas;
- operaciones;

como módulos técnicos independientes.

Debe pensar en:

- buscar;
- entender;
- decidir;
- actuar;
- completar.

---

# 2. Journey principal

Journey oficial:

Inicio
→ Buscar
→ Resultados
→ Mapa
→ Zona
→ Propiedad
→ Intelligence
→ Visita
→ Oferta/Puja
→ Operación
→ Documentación
→ Contrato
→ Firma
→ Pago
→ Finalización
→ Historial

La transición entre pasos debe sentirse natural.

---

# 3. Navegación principal

La navegación principal visible será aproximadamente:

- Inicio
- Buscar
- Intelligence
- Publicar
- Actividad
- Mi BenHouse
- Mensajes
- Perfil/Acceso

No deben aparecer como navegación principal:

- Pagos
- Contratos
- Documentos
- Ofertas
- Visitas

Estos viven dentro de contextos específicos.

---

# 4. Inicio

Objetivo:

transmitir rápidamente qué es BenHouse y permitir comenzar una búsqueda.

Elementos principales:

- fotografía inmobiliaria de alta calidad;
- buscador prominente;
- Comprar / Alquilar / Invertir;
- ubicación;
- CTA Buscar viviendas.

Después:

- zonas destacadas;
- propiedades destacadas;
- contexto de Intelligence;
- confianza/verificación;
- acceso a publicar.

Evitar:

- exceso de texto corporativo;
- múltiples bloques técnicos;
- “IA” como protagonista visual.

---

# 5. Search

Search debe ser uno de los mejores elementos del producto.

Requisitos:

- rápido;
- claro;
- filtros completos;
- sincronizado con mapa;
- responsive;
- resultados con fotografía protagonista.

Filtros principales:

- operación;
- modalidad;
- ubicación;
- precio;
- habitaciones;
- baños;
- superficie;
- tipología;
- características;
- disponibilidad.

No mostrar todos los filtros a la vez si empeora UX.

Utilizar progressive disclosure.

---

# 6. Resultados

Cada tarjeta debe priorizar:

- fotografía;
- precio;
- ubicación;
- habitaciones;
- baños;
- superficie;
- tipo/modalidad;
- favorito.

Puede mostrar una única señal inteligente relevante:

- Alta demanda
- Precio competitivo
- Buena oportunidad

No mostrar simultáneamente múltiples scores y badges.

---

# 7. Lista + mapa

En escritorio:

puede existir vista combinada.

En tablet/móvil:

adaptar composición.

Lista y mapa comparten el mismo estado de búsqueda.

No reiniciar filtros al cambiar de vista.

---

# 8. Mapa

Objetivo principal:

descubrir inmuebles geográficamente.

Debe incluir:

- markers;
- precio;
- clustering;
- selección de marker;
- zoom;
- viewport;
- búsqueda al mover mapa;
- dibujo de zona;
- multizona cuando esté habilitado;
- filtros sincronizados.

No convertir el mapa normal en un dashboard financiero.

---

# 9. Intelligence Map

Objetivo:

entender el mercado.

No mostrar todas las capas simultáneamente.

Una capa principal activa cada vez.

Ejemplos:

- demanda;
- precio;
- oferta;
- disponibilidad;
- oportunidades.

El usuario debe comprender qué está viendo sin explicación técnica.

---

# 10. Ficha de zona

Ejemplo:

Punta Prima

Debe poder mostrar:

- nivel de demanda;
- oferta disponible;
- precio medio;
- precio por m²;
- evolución;
- alquiler estimado;
- contexto;
- propiedades destacadas;
- oportunidades.

No forzar Top 10 si los datos no justifican ranking exacto.

Usar títulos contextuales:

- Más demandadas
- Oportunidades
- Precio competitivo
- Propiedades destacadas

según datos.

---

# 11. Ficha de inmueble

Orden visual recomendado:

1. Galería
2. Precio + información principal
3. CTAs
4. Descripción
5. Características
6. Ubicación/mapa
7. Intelligence
8. Confianza/verificación
9. Disponibilidad cuando proceda
10. Anunciante
11. Relacionados

CTAs principales según contexto:

- Solicitar visita
- Contactar
- Hacer oferta
- Reservar cuando corresponda
- Participar en puja cuando corresponda

---

# 12. Intelligence en inmueble

Debe responder preguntas:

- ¿Está bien de precio?
- ¿Cómo se compara con similares?
- ¿Cómo es la demanda?
- ¿Qué ocurre en esta zona?
- ¿Qué oportunidad representa?

Mostrar:

- lenguaje humano;
- métricas relevantes;
- confianza/metodología cuando sea útil.

Evitar:

- dashboard complejo;
- scores arbitrarios;
- falsa precisión.

---

# 13. Alquiler

La misma base visual de Property se adapta.

## Larga duración

Mostrar:

- precio mensual;
- disponible desde;
- condiciones;
- duración.

## Temporada

- fechas;
- periodo;
- condiciones.

## Vacacional

- calendario;
- fechas disponibles;
- entrada/salida;
- precio.

## Habitación

- habitación concreta;
- vivienda compartida;
- zonas comunes;
- disponibilidad específica.

No crear cuatro productos visuales completamente distintos.

---

# 14. Favorito

Acción inmediata y reversible.

El usuario debe poder:

- añadir;
- quitar;
- ver favoritos;
- entender si Listing deja de estar disponible.

Si baja precio:

mostrar claramente:

- precio anterior;
- precio nuevo;
- diferencia cuando sea útil.

---

# 15. Alertas

Guardar búsqueda debe ser sencillo.

El usuario puede decidir:

- recibir alertas;
- frecuencia cuando corresponda;
- desactivar.

No saturar con notificaciones.

Alertas deben ser relevantes y accionables.

---

# 16. Solicitar visita

Flujo corto:

1. CTA Solicitar visita
2. seleccionar fecha/hora
3. mensaje opcional
4. confirmar
5. estado visible

Después:

- Activity;
- Mi BenHouse;
- mensajes;
- recordatorios.

No crear aplicación independiente de agenda para usuario normal.

---

# 17. Oferta

CTA:

Hacer oferta

Flujo:

1. importe;
2. condiciones opcionales;
3. validez;
4. resumen;
5. confirmación.

Antes de enviar:

mostrar claramente:

“Estás enviando una oferta por X €”.

No utilizar lenguaje financiero innecesariamente complejo.

---

# 18. Negociación

Las revisiones/contraofertas deben presentarse como una conversación económica clara.

Ejemplo visual:

Tu oferta: 280.000 €
Contraoferta: 290.000 €
Tu nueva oferta: 285.000 €

Mantener historial.

No ocultar propuesta anterior.

---

# 19. Pujas

Solo aparecen cuando Listing usa Auction.

Mostrar:

- estado;
- tiempo restante;
- reglas;
- importe relevante;
- número de participantes cuando esté permitido;
- CTA.

La UX no puede parecer:

- casino;
- apuestas;
- gamificación.

Debe transmitir:

proceso inmobiliario estructurado.

---

# 20. Publicar inmueble

Utilizar wizard.

Pasos orientativos:

1. Operación
2. Inmueble
3. Ubicación
4. Características
5. Fotografías
6. Precio
7. Disponibilidad/modalidad
8. Verificación/documentación
9. Vista previa
10. Publicar

Guardar borrador automáticamente.

No mostrar 70 campos en una única pantalla.

---

# 21. Verificación progresiva

No pedir máxima fricción al inicio.

Ejemplo:

### Explorar
sin KYC.

### Crear cuenta
email/phone.

### Hacer acciones sensibles
mayor verificación.

### Publicar/operar
requisitos necesarios.

La UX debe explicar:

- qué se pide;
- por qué;
- para qué;
- quién lo puede ver.

---

# 22. Mi BenHouse

Un único espacio contextual.

No construir webs diferentes para:

- comprador;
- propietario;
- inversor.

El contenido se adapta a actividad real.

Ejemplo de resumen:

- próxima visita;
- 2 acciones pendientes;
- una oferta recibida;
- una propiedad favorita bajó de precio;
- una operación activa.

Secciones contextuales:

- Guardados
- Visitas
- Ofertas
- Operaciones
- Propiedades
- Documentos
- Intelligence

Mostrar solo lo relevante.

---

# 23. Centro de actividad

Objetivo:

responder:

- ¿qué ha ocurrido?
- ¿qué tengo que hacer?

Ejemplo:

Hoy

“Tu documento ha sido validado.”

“Una vivienda guardada ha bajado 12.000 €.”

Mañana

“Visita — 11:30.”

Pendiente

“Falta firmar el contrato.”

Activity y Task pueden convivir visualmente, pero deben distinguirse.

---

# 24. Tareas

Las Tasks deben ser accionables.

Ejemplos:

- Subir documento
- Firmar contrato
- Reintentar pago
- Completar verificación

CTA lleva directamente al punto correcto.

No crear tareas informativas que no requieren acción.

---

# 25. Operación

Una Operation debe tener una vista única.

Ejemplo:

Compra — Apartamento Punta Prima

Progreso:

1. Oferta aceptada ✓
2. Identidad ✓
3. Documentación ●
4. Contrato ○
5. Firma ○
6. Pago ○
7. Finalización ○

Debajo:

- siguiente acción;
- requisitos;
- documentos;
- participantes;
- actividad;
- ayuda.

No obligar al usuario a navegar por módulos independientes.

---

# 26. Progress stepper

El stepper es una proyección de Operation y Requirements.

No debe inventar estados.

El backend proporciona:

- estado actual;
- pasos completados;
- pasos pendientes;
- bloqueos.

Frontend representa.

---

# 27. Documentación

Dentro de Operation o contexto apropiado.

Ejemplo:

DNI
Validado

Escritura
En revisión

Documento X
Pendiente

Cada documento debe explicar:

- qué es;
- por qué se necesita;
- estado;
- quién puede verlo cuando sea relevante.

---

# 28. Firma

UX:

Contrato preparado
→ Ver contrato
→ Firmar
→ Esperando otras firmas
→ Firmado

Aunque se abra proveedor externo/sandbox:

BenHouse mantiene contexto.

Al volver:

estado actualizado desde backend.

No mostrar “firmado” basándose solo en redirect.

---

# 29. Pago

Pantalla simple.

Mostrar:

- concepto;
- importe;
- desglose;
- método;
- estado.

Estados UX:

- Pendiente
- Procesando
- Confirmado
- No completado / Reintentar

No mostrar mensajes técnicos del PSP al usuario sin traducción.

---

# 30. Operación completada

Al completar:

mostrar:

“Operación completada”

y resumen relevante.

Después:

Historial.

No eliminar la operación de Mi BenHouse simplemente porque terminó.

---

# 31. Historial

Debe permitir consultar:

- inmueble;
- fechas;
- estado final;
- participantes relevantes;
- contrato;
- pagos autorizados;
- documentos autorizados;
- acontecimientos principales.

No mostrar AuditEvent técnico completo.

---

# 32. Mensajes

Lista:

- contexto de inmueble;
- persona/organización;
- último mensaje;
- fecha;
- unread.

Conversación:

- referencia visible a Listing/Operation;
- mensajes;
- CTAs contextuales cuando correspondan.

No crear WhatsApp genérico.

---

# 33. Propietario

Dentro de Mi BenHouse.

### Mis propiedades

Mostrar:

- fotografía;
- estado;
- precio;
- visitas;
- favoritos;
- contactos;
- ofertas.

### Rendimiento

Métricas privadas:

- views;
- favorites;
- contacts;
- visits;
- offers.

No visibles públicamente.

---

# 34. Profesional / Agencia

Puede utilizar navegación lateral/contextual más densa.

Secciones:

- Resumen
- Cartera
- Leads
- Agenda
- Mensajes
- Ofertas
- Operaciones
- Intelligence

No superar complejidad necesaria.

---

# 35. Dashboard profesional

Debe mostrar información accionable.

Ejemplos:

- leads nuevos;
- visitas próximas;
- ofertas pendientes;
- operaciones activas;
- propiedades con bajo rendimiento;
- demanda relevante;
- Match detectados.

No mostrar métricas solo porque existen.

---

# 36. CRM

La UX debe sentirse conectada a BenHouse.

Ejemplo Lead:

- datos autorizados;
- inmueble relacionado;
- conversación;
- visitas;
- ofertas;
- estado;
- notas;
- tarea.

No introducir doble entrada de datos innecesaria.

---

# 37. Match

Presentación:

“Este cliente coincide con 6 propiedades de tu cartera.”

o:

“Existe fuerte demanda para inmuebles similares.”

Mostrar razones relevantes:

- zona;
- presupuesto;
- habitaciones;
- modalidad.

No mostrar score sin explicación.

---

# 38. Inversor

v0.4 mantiene experiencia ligera.

Accesos:

- zonas;
- oportunidades;
- Intelligence;
- favoritos;
- comparativas.

No dashboard financiero enterprise.

---

# 39. Confianza BenHouse

Mostrar indicadores simples.

Ejemplos:

✓ Identidad verificada
✓ Inmueble verificado
✓ Agencia verificada

CTA:

“Ver por qué”

Al desplegar:

explicación segura.

No mostrar:

- score opaco;
- señales antifraude;
- evidencias sensibles.

---

# 40. Admin

Admin es funcional, no prioridad visual premium.

Necesita:

- filtros claros;
- estados;
- acciones;
- motivos;
- auditoría.

Áreas:

- usuarios;
- publicaciones;
- verificaciones;
- documentos;
- incidencias;
- operaciones;
- pagos;
- audit.

No construir ERP.

---

# 41. Empty states

Obligatorios.

Ejemplos:

Favoritos:
“Aún no has guardado ninguna vivienda.”

Visitas:
“No tienes visitas programadas.”

Search:
“No hemos encontrado propiedades con estos filtros.”

Operaciones:
“No tienes operaciones activas.”

Siempre que sea útil:

añadir siguiente acción.

No utilizar “No data”.

---

# 42. Loading states

Todas las vistas principales necesitan loading adecuado.

Utilizar:

- skeletons;
- progressive loading;
- placeholders.

Evitar flashes bruscos.

No bloquear toda pantalla si solo carga un bloque secundario.

---

# 43. Error states

Errores deben:

- ser comprensibles;
- explicar siguiente acción;
- permitir reintento cuando proceda.

No mostrar:

- stack traces;
- error codes internos;
- raw provider errors.

---

# 44. Permission denied

Diferenciar cuando sea apropiado:

- no autenticado;
- sin permiso;
- recurso no disponible.

No revelar existencia de recursos privados.

---

# 45. Success states

Acciones críticas deben confirmar resultado.

Ejemplos:

“Visita solicitada.”

“Oferta enviada.”

“Documento enviado para revisión.”

“Pago confirmado.”

Evitar toasts genéricos tipo:

“Success”.

---

# 46. Responsive

Tres contextos:

## Desktop

Experiencia completa.

## Tablet

Layouts adaptados.

## Mobile web

Acciones críticas totalmente utilizables.

No simplemente reducir desktop.

---

# 47. Mobile Search

En móvil:

- filtros mediante panel/modal;
- lista prioritaria;
- mapa accesible mediante toggle;
- CTA visibles;
- navegación simplificada.

No intentar mostrar mapa + lista + filtros completos simultáneamente.

---

# 48. Mobile Operation

Debe ser especialmente clara.

Stepper vertical/compacto.

Acción pendiente destacada.

Documentos, firma y pago utilizables con una mano cuando sea razonable.

---

# 49. Navegación móvil

Utilizar patrón simple.

Puede incluir:

- Inicio
- Buscar
- Actividad
- Mi BenHouse

y acceso a otros elementos contextual.

No trasladar toda navegación desktop a una barra inferior gigantesca.

---

# 50. Accesibilidad

v0.4 debe incluir como mínimo:

- contraste suficiente;
- labels;
- navegación por teclado razonable;
- focus visible;
- alt text;
- botones con nombres accesibles;
- formularios con errores asociados;
- no depender solo del color.

Objetivo mínimo:

buenas prácticas compatibles con WCAG 2.1 AA en componentes críticos.

No declarar certificación formal sin auditoría.

---

# 51. Formularios

Principios:

- pedir solo información necesaria;
- validación clara;
- errores junto al campo;
- preservar información si falla submit;
- autoguardado en flujos largos;
- no pedir dos veces datos ya conocidos.

---

# 52. Feedback inmediato

Acciones simples:

Favorite
→ feedback instantáneo.

Acciones complejas:

Offer
Payment
Signature

→ mostrar estado real.

No fingir completion para mejorar sensación de rapidez.

---

# 53. Progressive disclosure

BenHouse tiene mucha información.

No mostrarla toda inicialmente.

Ejemplo Property:

primero:
- precio;
- características;
- CTA.

Después:
- Intelligence;
- detalles;
- confianza;
- comparables.

La profundidad está disponible sin saturar.

---

# 54. Decision Layer

Toda funcionalidad importante debe responder a una pregunta.

Search:
¿Qué propiedades encajan?

Map:
¿Dónde están?

Intelligence:
¿Cuál tiene sentido?

Comparables:
¿Está bien de precio?

Demand:
¿Qué interés existe?

Trust:
¿Puedo confiar?

Visit:
¿Quiero verla?

Offer:
¿Quiero actuar?

Operation:
¿Qué falta para terminar?

Si una pantalla no ayuda a descubrir, entender, decidir, actuar o completar:

cuestionar su inclusión.

---

# 55. IA en UX

Evitar etiquetas constantes:

“Powered by AI”
“IA BenHouse”
“AI Score”

Preferir:

“Precio competitivo respecto a propiedades similares.”

“Alta demanda en esta zona.”

Si IA genera explicación:

debe basarse en métricas estructuradas.

No presentar inferencias como hechos.

---

# 56. Métricas

Mostrar métricas con contexto.

Incorrecto:

Demand Score: 83

Mejor:

Demanda alta

cuando el usuario puede ampliar:

- metodología;
- periodo;
- sample size;
- confidence.

---

# 57. Colores de estado

No depender únicamente del color.

Ejemplo:

✓ Validado
● En revisión
! Requiere acción

Color refuerza, texto comunica.

---

# 58. Animaciones

Utilizar de forma mínima:

- transiciones;
- loading;
- feedback.

No añadir animaciones llamativas que compitan con propiedades.

La sensación premium debe venir de:

- jerarquía;
- espacio;
- tipografía;
- fotografía;
- velocidad.

---

# 59. SEO UX

Páginas públicas importantes deben ser indexables cuando corresponda:

- Listing;
- Location/Zone;
- categorías.

Pero no indexar:

- account;
- operations;
- messages;
- private dashboards.

SEO técnico se especificará/implementará en fase correspondiente.

---

# 60. Breadcrumbs

Útiles en contextos como:

España
→ Alicante
→ Orihuela Costa
→ Punta Prima
→ Listing

No necesarios en cada pantalla interna.

---

# 61. URLs

URLs públicas deben ser comprensibles y estables cuando sea posible.

Ejemplo conceptual:

/comprar/vivienda/punta-prima/...
/zona/punta-prima

La definición final de rutas puede ajustarse durante implementación.

No incluir IDs sensibles como único elemento si existe slug seguro.

La autorización no depende del slug.

---

# 62. Demo visual

La demo v0.4 debe utilizar:

- fotografías inmobiliarias premium;
- propiedades coherentes;
- datos realistas;
- zonas reconocibles;
- mapas reales;
- estados demo preparados.

No utilizar:

- Lorem Ipsum;
- imágenes aleatorias rotas;
- precios absurdos;
- dashboards vacíos.

---

# 63. Demo story — Usuario

La interfaz debe permitir demostrar:

1. María abre BenHouse.
2. Busca en Alicante.
3. Explora mapa.
4. Entra en Punta Prima.
5. Consulta Intelligence.
6. Abre inmueble.
7. Lo guarda.
8. Recibe bajada de precio.
9. Solicita visita.
10. Realiza oferta.
11. Oferta aceptada.
12. Entra en Operation.
13. Completa documentación.
14. Contrato.
15. Firma sandbox.
16. Pago sandbox.
17. Operation completada.
18. Historial.

No debe requerir navegar a paneles técnicos para completar la historia.

---

# 64. Demo story — Profesional

1. Profesional accede.
2. Ve cartera.
3. Ve demanda.
4. BenHouse muestra Match.
5. Abre Lead.
6. Contacta.
7. Programa visita.
8. Gestiona Offer.
9. Operation.
10. Ve resultado/rendimiento.

Debe demostrar:

CRM + Intelligence + demanda.

---

# 65. UX anti-clutter

Antes de añadir un elemento visual:

preguntar:

- ¿es necesario?
- ¿ayuda a decidir?
- ¿tiene prioridad?
- ¿puede esconderse tras detalle?
- ¿duplica algo?

Eliminar elementos que compitan sin aportar.

---

# 66. Consistencia

Componentes equivalentes deben comportarse igual.

Ejemplos:

- Favorite;
- status badge;
- CTA principal;
- modal;
- form errors;
- cards.

No crear un diseño diferente por cada módulo.

---

# 67. Design tokens

La UX consumirá tokens definidos en `09-DESIGN-SYSTEM.md`.

No hardcodear decisiones visuales aleatorias dentro de cada página.

---

# 68. UX analytics

Medir en futuro:

- search success;
- filter use;
- property view;
- favorite;
- visit conversion;
- offer conversion;
- operation completion;
- drop-off.

Pero no utilizar analytics para bloquear MVP.

---

# 69. Rendimiento percibido

Search y Property deben sentirse rápidos.

Aplicar:

- skeletons;
- image optimization;
- progressive loading;
- optimistic UI solo donde sea seguro.

No utilizar optimistic state para:

- payment confirmed;
- contract signed;
- offer accepted.

---

# 70. Copywriting

Idioma base:

español.

Texto:

- humano;
- directo;
- breve;
- profesional.

Evitar:

- tecnicismos;
- anglicismos innecesarios;
- marketing exagerado.

“Intelligence” puede mantenerse como concepto de marca/producto aprobado, pero las explicaciones deben ser comprensibles.

---

# 71. Filosofía BenHouse

La UX debe representar:

- claridad;
- confianza;
- control;
- información útil;
- continuidad;
- tecnología invisible;
- experiencia premium.

El usuario debe sentir:

“BenHouse me ayuda a avanzar.”

No:

“BenHouse tiene muchas funcionalidades.”

---

# 72. Criterio de cierre UX

UX se considera correctamente implementada cuando:

- Search es usable y rápida;
- Map y list están sincronizados;
- Property comunica información clave;
- Intelligence ayuda a decidir;
- los CTAs son claros;
- Visit es sencilla;
- Offer es comprensible;
- Operation centraliza el proceso;
- Documents/Contract/Signature/Payment no parecen productos separados;
- Mi BenHouse se adapta al usuario;
- CRM es accionable;
- responsive funciona;
- estados loading/error/empty existen;
- no existe sobrecarga visual;
- las dos demo stories pueden completarse sin explicación técnica.
